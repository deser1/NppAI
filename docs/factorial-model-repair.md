`wygeneruj kod na silnię`. It does not promote NppAI as a general coding model.

unchanged and available.

## Reproducible measurement

`scripts/factorial_repair.py` initializes from the SHA-pinned rc.2 own dense v2
checkpoint. The final protocol uses seed47, 4096 AdamW updates at0.0003, four
original direct examples and four factorial examples per batch. There are532
authored factorial training records, including four plain Polish training
probes. The original96 direct training records provide retention replay.
All loss is per-example completion loss; no test case is part of training.

A fixed256-byte user-prompt boundary for the aligned branch is an explicit
optional service setting.
A separate optional width8 beam decoder selects model-generated bytes using
only generic AST, requested declaration and name-binding checks. It may prefill
an explicit, unambiguous requested function header. It cannot access factorial
algorithms, reference answers or test cases. Structurally valid wrong functions
are still possible. Unchanged/default backends keep their existing greedy
format and behavior. For an explicit requested declaration, the optional
profile first accepts a complete, structurally valid, value-returning greedy
function using the legacy prompt format. Otherwise it uses the aligned beam.
This is generic structural routing, without task-name or reference-answer
lookup. The aligned branch rejects formatted task/context longer than256
UTF-8 bytes; long repair feedback may therefore be unavailable.

The report preserves old greedy output, original weights with the new profile,
repaired greedy output and repaired
production NumPy decoding independently. It includes18 authored development
probes:12 configurations of one alternative description (two names, three
parameters, two modes), four new-name rows and two reproduction rows. These are
exposed development probes, not a blind benchmark. Four simple Polish prompts
are separately labelled as training memorization probes.

The CI publication gate requires:

- Actual restricted Docker execution, with18 correct reference controls and a
  deliberately wrong constant-return negative control.
- Both reproduction rows and all four Polish training probes pass; at least
  eight of12 wording rows pass. New names are reported even when they fail.
- None of the original88 direct exact hits is lost, both in raw legacy readout
  and in the actual new production profile; all96 outputs for each are retained.
- Actual NumPy/Torch greedy agreement on three concrete requests, with model
  state unchanged during readout.
- A real portable Notepad++ window sends the Polish request to the packaged
  service. Its readable review bytes must equal the actual Docker-tested
  candidate, and model/service/recording identities must match the evidence.
  A test-only server bootstrap records the actual returned response unchanged;
  the literal legacy diff rendering is retained separately, including its extra
  displayed final line. This avoids inferring exact model bytes from the diff.
- Exact merged-main CI succeeds before a new experimental model release.

These are narrow release criteria, not general correctness criteria. Generated
code still needs task-specific tests. There is no hidden fallback algorithm.

## Rejected attempt retained

[rejected-v1.zip](evidence/factorial-repair/rejected-v1.zip) contains the first
reconstructed2048-update pilot's frozen protocol, trace and raw report. It
retained88 original hits and reached96/96 original training exact, but only two
of12 alternative-wording outputs matched the reference after search. Its four
plain Polish probes matched; no Docker execution was available for that local
pilot. It failed the intended wording gate and was not published. The final
protocol expands description coverage and uses4096 updates. This is a second
attempt on exposed development tasks, not an independent confirmation.

The historical staged-protocol training workflow still references an expired
GitHub Actions initialization artifact (`11775752592`, HTTP410 on26Oct2026).
Its old experiment cannot currently be rerun without restoring those exact
source weights. This repair leaves that pilot unchanged and has its own trainer
using the permanent, SHA-pinned rc.2 model release.

## Windows demonstration and remaining check

The `Bounded factorial model repair` workflow records actual generation in the
published rc.2 x64 plugin, using an extracted new service ZIP and the measured
new checkpoint. Linux Docker functional execution and Windows request/review
are separate checks. The hosted Windows job has no Docker Desktop and keeps
Apply disabled. Its GIF must not be described as validated GUI Apply/Undo.

For the complete interactive Windows path, run the following from the exact
model-release source checkout, on a Windows x64 desktop with Python3.12,
GitHub CLI and Docker Desktop configured for Linux containers:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/windows_validated_smoke.ps1
```

The script downloads/checks release assets, pulls a trusted Python image,
resolves its immutable local image ID, verifies positive/negative Docker
controls, launches a fresh portable editor and real model service, generates
into an empty Python buffer, requires Apply after validation, applies the
actual proposal and verifies one Undo restores the empty buffer. It preserves
raw UI events, server log, model identity and the actual window recording in
the printed evidence directory. This path remains **unverified until run on
that environment**. Existing-installation upgrade also remains unverified.
No fixture validator or prewritten proposal substitutes for this check.
